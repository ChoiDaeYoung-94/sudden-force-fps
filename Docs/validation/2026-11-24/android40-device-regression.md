# Android 코드 40 산출물과 기기 회귀 검증

## 같은 빌드 확인

Unity 6000.3.25f1에서 소스 `d65fe6d3fea1e238e7eaa8e8811916757e333e07`를 일반 Android 1.0.200(40)으로 내보냈다. Intro, Login, Lobby, Room, DesertHouse 다섯 씬을 포함한다. Unity 결과는 오류 0건·경고 68건이다. Gradle release APK와 AAB에 대해 다음 SHA-256을 비교할 수 있다.

| --- | ---: | --- |
| 무서명 APK | 106784607 | `6D66039AA8504B2C016F65CDB3843CAAD197EBC7F29FD5EEDA6B8955FA28EEC3` |

Android 빌드 도구의 `apksigner verify --verbose`로 설치용 APK의 v2 서명을 확인했다. APK 내부 143개 엔트리의 압축 해제 바이트가 무서명본과 같다. `bundletool validate`, manifest, APK의 ZIP 배치와 두 패키지의 ELF LOAD 정렬을 확인했다. 최소 API 25, 대상 API 36, arm64-v8a이며 네이티브 라이브러리 7개가 두 패키지에서 동일하다. 16 KB 검사는 정적 검사다. 심볼은 6개가 일치했고 `libnanosockets.so`는 빠져 있다. 정식 업로드 키 서명과 Play 제공은 별도 단계다.

LastBuild의 packedAssets 6,861행을 대조했다. Assets/Packages 경로는 중복을 제외해 2,811개다. 그 밖의 36행은 Unity 내장 리소스 26, 내장 이름 3, preload 6, Quad D 영상 1이다. 영상은 APK와 AAB 모두 원본 88,032바이트가 일치한다. 코드 38 대비 새 공개 경로는 오른쪽 보행 클립 하나다. 기존 Raw9 클립 9개와 새 클립이 포함됐고, 별도 감시한 원본 22개 경로와 비공개 6개 경로는 packedAssets에 없었다. 배포 고지 바이트를 대조했으며 에셋별 상업 이용 권리는 별도 확인 대상이다.

## 콜드 시작과 기기 보존

- LDPlayer의 별도 인스턴스에 일반 패키지를 로컬 테스트 서명으로 설치했다. 1280×720, RAM 4096 MiB, 4 vCPU의 첫 기동과 재기동에서 검은 화면이 관찰됐다. 같은 설치를 2 vCPU로 다시 기동하자 원본 Quad D의 세 구간이 순서대로 일치했다(평균 대조 점수 0.996). 게임의 Retry를 눌러 Google 로그인 입력 화면까지 확인했다. 계정 인증과 이 설치에서의 경기는 미검증이다. CPU 수와 결과의 동시 변화만 관측했다.
- SM-A175N은 기존 일반 코드 36 설치를 보존했다. 별도 앱 ID로 설치한 코드 40 시작 검증본은 `assets/`와 `lib/` 21개 파일이 전부 일반 APK와 바이트 단위로 일치한다. 두 번의 콜드 시작 영상은 Quad D 세 구간을 통과했고(0.972, 0.964) Android 재생 오디오와 원본 음원의 파형 상관은 모두 0.9981이었다. 표시된 움직임 기준으로 녹화 오디오가 뒤따른 중앙값은 147 ms와 96 ms였다. 기기 스피커의 실제 지연은 측정하지 않았다.
- 같은 소스의 독립적인 단일 씬 진단 앱에서 Red·Blue 프리팹을 Fusion Single로 생성했다. A17의 OpenGL ES 3, 2340×1080 화면 녹화와 12조건×48 샘플을 확보했다. 카메라 위치를 고정해 기존 판정 자세와 렌더용 왼손을 대조했다. 오른쪽 보행의 48위상 밑창 높이 범위는 양 팀 모두 80.335 mm에서 0.857 mm로 줄었다. 고정 스폰 원점 기준 보정 후 최저점은 −15.530 mm였다. 경기 중 캐릭터 컨트롤러가 지지면에 둔 위치와 구분한다. 진단 앱 삭제 후 기존 네 패키지의 UID·버전·설치 및 갱신 시각과 일반 앱 복귀를 확인했다.

## 이동 중 사망을 세 번째 플레이어가 보는 경우

1. 일반 코드 36 A17과 위 소스의 Editor 호스트를 같은 DesertHouse 방에 넣고, 독립 Windows 검증 Player를 세 번째 피어로 참가시킨다. 관찰 클라이언트에는 피해 캐릭터의 입력 권한과 상태 권한이 없다.
2. 호스트의 시작 위치를 테스트에서 잡고 정상 입력 경로로 호스트를 이동시킨다. A17의 실제 FIRE 터치로 호스트를 처치한다. 권한 측 고정 틱의 위치·속도·체력·생명 번호와 관찰자의 렌더 샘플을 따로 수집한다. 위치 변화가 없는 벽 앞 이동 입력은 정지 대조군으로 취급한다.
3. 새 생명의 자세를 받기 전에 이전 생명의 보행을 합성하는지 확인한다. 부활 체력, 첫 새 보행 위상, 일반 자세에서의 생명 번호 일치와 오류 횟수를 대조한다.

| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 이동 중 | 2.100 m/s | 2653 → 2845 | 100 | 570 | 328·58 | 176 | 6 / 2 |
| 정지 대조 | 0 m/s | 8257 → 8449 | 100 | 600 | 357·57 | 177 | 7 / 2 |

이동 경기의 사망 직전 다섯 위치에서 첫 위치와 마지막 위치의 Z 차이는 0.13125 m였다. 두 경기 모두 부활까지 64 Hz 기준 3초가 걸렸다. 관찰자에서 새 생명의 첫 일반 자세는 위상 0이었고 두 표본 모두 보행 오류가 없었다. 세 번째 피어의 렌더 틱에는 보간과 관찰 시점 차이가 있으므로 이 차이를 네트워크 지연으로 해석하지 않는다.
